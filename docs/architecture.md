# Архитектура: La Mia Fortuna Shoes

Дата: 2026-11-12. Автор: архитектор. Документ описывает, что уже есть в коде, какие решения приняты для запуска и почему. План работ лежит в `docs/tasks.md`.

## 1. Цель и контекст

Интернет-магазин женской обуви (Харьков, собственное производство). Клиентка нетехническая, сама ведет каталог через админку. Продажи пойдут из рекламы в Instagram, поэтому типичный покупатель:

- открывает ссылку на товар во встроенном браузере Instagram на телефоне;
- видит одну страницу товара (она и есть посадочная), решает за секунды;
- оформляет заказ без регистрации, часто наложенным платежом.

Из этого следуют приоритеты: скорость страницы товара на мобильном, корректное превью ссылки, надежное создание заказа, измеримость рекламы (события и источник заказа), минимум юридических рисков для рекламного кабинета и эквайринга.

## 2. Стек (без изменений)

- Next.js 14 App Router, TypeScript, Tailwind CSS.
- Prisma 5 + PostgreSQL (Supabase), фото в Supabase Storage (bucket `product-images`, public).
- Zustand (корзина в localStorage), Zod (валидация форм и API).
- Оплата: Monobank Acquiring (основной), LiqPay (запасной, переключается `PAYMENT_PROVIDER`), наложенный платеж.
- Доставка: Новая Почта, автокомплит города и отделения, ТТН вручную.
- Новое: Vitest (тесты чистых функций), GitHub Actions (typecheck, lint, test). Больше зависимостей не добавляем.

## 4. Что показал аудит кода (факты, на которых стоит план)

Работает и не трогаем: каталог, фильтры, поиск, корзина, чекаут, админка товаров/категорий/цветов/главной, сессии админки (подпись HMAC, httpOnly, secure, sameSite=lax, сравнение подписи за постоянное время), пароль scrypt, подпись вебхука Monobank (ECDSA, с обновлением ключа), миграции раскатываются на чистую БД по порядку. `npm run typecheck` и `npm run lint` проходят (lint дает только предупреждения про `<img>`).

Найденные проблемы (все покрыты задачами):

1. `package.json`: нет `postinstall: prisma generate` и скрипта `prisma migrate deploy`. Без первого сборка на Vercel упадет или возьмет устаревший клиент.
2. `POST /api/orders`: не проверяет, что товар опубликован и размер в наличии; нет ограничения количества; `request.json()` без обработки ошибки; номер заказа `GP-<timestamp>` (префикс от старого проекта, возможны коллизии).
3. Вебхуки оплаты: любой статус кроме `success` записывается как `FAILED`. У Monobank статусы `created/processing/hold` приходят до успеха, а порядок доставки не гарантирован, значит оплаченный заказ может стать `FAILED`. Сумма платежа не сверяется с суммой заказа. У LiqPay статус `sandbox` считается оплатой и в бою.
4. Страница `/thank-you` показывает только номер из URL: нет статуса оплаты, нет данных для события Purchase, пропущенный вебхук никак не догоняется.
5. Уведомлений о новом заказе нет вообще: клиентка узнает о заказе, только если сама откроет админку.
6. Метаданные: есть только общий title в корневом layout. Нет Open Graph, canonical, sitemap, robots, у товара нет своего title/description/картинки превью.
7. Аналитики нет (ни скриптов, ни событий, ни UTM).
8. Картинки: везде обычный `<img>` с оригиналом из Supabase (до 5 МБ на фото с телефона). Это главный риск скорости на мобильном.
9. Все публичные страницы `force-dynamic`: каждый просмотр ходит в БД (шапка, главная, товар).
10. Страница товара: кнопка "Замовити в Telegram" ведет на `https://t.me` (никуда), аккордеон "Про модель" с зашитым текстом про теплый мех показывается у всех товаров, включая летние.
11. Главная показывает 3 отзыва-заглушки из сида как настоящий блок.
12. Телефон и ссылки на соцсети зашиты в 5 файлах; `/privacy` не слинкована из футера; публичной оферты нет; согласия на обработку данных на чекауте нет.
13. Админка: пункт "Промокоди" ведет на заглушку, `POST /api/admin/promocodes` пишет в БД тело запроса без валидации; пункт "Імпорт" (Excel) остался от шаблона; загрузка фото принимает любой `image/*` (включая SVG и HEIC), расширение берется из имени файла; логин без ограничения попыток.
14. `next.config.mjs`: `images.remotePatterns` разрешает любой хост (открытый прокси картинок, если включить оптимизацию), нет базовых заголовков безопасности.
15. Документация: README описывает шаблон с личным кабинетом, CLAUDE.md говорит, что сид "очищує й пересоздає" (уже неправда), гайда по админке в репозитории нет.

## 5. Ключевые решения и почему

### 5.1 Деплой: Vercel + Supabase

- Vercel, проект из GitHub-репозитория, ветка `main` = production. Регион функций `fra1` (Франкфурт), потому что БД Supabase в `eu-central-1`; иначе каждый запрос к БД идет через океан. Фиксируем в `vercel.json`.
- Две БД: текущая Supabase остается для разработки и Preview-окружения Vercel, для production создается отдельный проект. Preview-деплои никогда не получают прод-ключи.
- `DATABASE_URL` через pooler (порт 6543, `?pgbouncer=true&connection_limit=1` для serverless), `DIRECT_URL` только для миграций.
- Миграции на прод накатывает человек с локальной машины командой `npm run prisma:deploy` после бэкапа. В сборку Vercel миграции не включаем: так ошибка миграции не ломает деплой и не происходит без присмотра.
- `postinstall: prisma generate` обязателен для Vercel.
- Вебхук Monobank не настраивается в кабинете: адрес передается в каждом счете из `NEXT_PUBLIC_SITE_URL`, поэтому эта переменная на проде обязана быть финальным https-доменом.
- Тарифы: Hobby на Vercel не для коммерции, бесплатный Supabase засыпает и не имеет бэкапов. Решение о платных тарифах за человеком (см. вопросы), архитектура от тарифа не зависит.

### 5.2 Заказ и оплата

- Логику расчета заказа выносим в чистую функцию (`src/lib/orders/build-order.ts`) и покрываем тестами: цены берутся только из БД, недоступные позиции (товар скрыт, размер отмечен "немає", вариант удален) возвращают 409 с понятным текстом. Остаток не уменьшаем: по договоренности с клиенткой `stock` это флаг наличия (1/0), а не складской учет.
- Номер заказа `LMF-YYMMDD-XXXX` (4 случайных символа без похожих букв): читается по телефону, не раскрывает время с точностью до миллисекунды, при коллизии повтор.
- Статус оплаты меняет одна чистая функция `resolvePaymentUpdate` с правилами: промежуточные статусы игнорируются; `PAID` не понижается (кроме возврата); `PAID` ставится только при совпадении суммы и номера счета. Обновление в БД условное (по прежнему статусу), чтобы вебхук и сверка не сработали дважды.
- Страница `/thank-you` читает заказ на сервере и показывает состояние. Если оплата картой еще `PENDING`, сервер сам спрашивает статус счета у Monobank и применяет его той же функцией. Это закрывает пропущенный вебхук без кронов и очередей.
- Сводка заказа для `/thank-you` не содержит персональных данных (только состав, сумма, статус), потому что номер заказа приходит из URL.
- Оплату картой можно выключить флагом `NEXT_PUBLIC_ONLINE_PAYMENT_ENABLED=false`: запуск возможен до получения боевого токена Monobank, чекаут покажет только наложенный платеж.
- Уведомления клиентке: Telegram-бот (бесплатно, без домена и почтового сервиса, у клиентки Telegram уже рабочий канал). Сообщение при создании заказа и при успешной оплате. Сбой Telegram никогда не ломает заказ. Письма покупателю не делаем: email на чекауте необязательный, подтверждение идет звонком или сообщением менеджера.
- Повторная оплата неудачного платежа и промокоды в план не входят (см. бэклог).

### 5.3 Безопасность

- Сессии админки оставляем как есть (решение уже рабочее). Добавляем: ограничение попыток логина, белый список типов файлов при загрузке, удаление невалидируемого `POST /api/admin/promocodes`, заголовки безопасности, ограничение хостов картинок.
- Ограничитель запросов в памяти процесса (логин, создание заказа, прокси Новой Почты). На serverless это защита "в меру": счетчик живет в одном экземпляре функции. Для настоящей защиты человек включает правило rate limit в Vercel Firewall. Redis и подобное не добавляем: несоразмерно магазину.
- Content-Security-Policy не вводим: с Pixel и GA4 он требует постоянного сопровождения, польза для этого сайта мала.
- `scripts/check-env.mjs` проверяет набор переменных перед деплоем (нет заглушек, секрет нужной длины, URL не localhost).

### 5.4 Трафик из Instagram: превью ссылок и SEO

- `metadataBase` из `NEXT_PUBLIC_SITE_URL`, общие Open Graph теги, картинка по умолчанию генерируется кодом (`opengraph-image.tsx`, только латиница, чтобы не тянуть шрифт с кириллицей).
- Страница товара: свой title, description, canonical, `og:image` = первое фото товара, цена в мета-тегах `product:price:*`, JSON-LD `Product`. Это нужно для превью в Instagram/Telegram/Viber и пригодится для каталога Meta.
- Категории и статические страницы: title и canonical без параметров фильтров. Корзина, чекаут, благодарность, поиск: `noindex`.
- `sitemap.xml` (товары, категории, статические страницы) и `robots.txt` (закрыты `/admin`, `/api`, корзина, чекаут). Генерируются динамически, чтобы сборка не зависела от БД.
- Ссылки для рекламы: адрес товара `/product/<slug>`, slug создается один раз из названия и при редактировании не меняется (проверено по коду: форма slug не отправляет). В админке добавляем кнопку "Скопіювати посилання". UTM-метки клиентка в ссылку руками не пишет: в рекламном кабинете они задаются шаблоном параметров URL (описываем в гайде).

### 5.5 Аналитика и рекламные события

Что реально нужно и почему:

- Meta Pixel - обязательно: без событий реклама в Instagram не оптимизируется на покупки.
- GA4 - да: бесплатный независимый взгляд на воронку, ставится тем же кодом.
- Четыре события воронки: просмотр товара, добавление в корзину, начало оформления, покупка. Больше не нужно.
- UTM и `fbclid` сохраняем в заказ (поле `Order.attribution`, JSON). Это единственный источник правды "какая реклама дала заказ", который не зависит от блокировок Pixel во встроенном браузере и iOS. Клиентка видит источник в карточке заказа и в Telegram.
- Баннер согласия на cookie не делаем: аудитория в Украине, закон требует согласия на обработку персональных данных (даем строкой у кнопки заказа со ссылками на оферту и политику), а блокирующий баннер режет конверсию во встроенном браузере. Если реклама пойдет на ЕС, потребуется Consent Mode (в бэклоге).
- Meta Conversions API (серверные события) откладываем: нужен токен и настройка в Business Manager. Архитектура к нему готова: `eventID` покупки равен номеру заказа, `fbclid` хранится в заказе.

Как устроено:

- `src/lib/analytics/events.ts` - чистые функции: одно внутреннее событие превращается в параметры GA4 и Meta Pixel (валюта UAH). Покрыто тестами.
- Идентификатор товара в событиях = slug товара. Он есть и на странице товара, и в корзине, и в заказе; при создании каталога Meta тот же slug станет id товара.
- `track()` молча ничего не делает, если скрипты не загружены (нет ID в окружении, блокировщик). Скрипты грузятся через `next/script` (`afterInteractive`) только в публичной части и только если заданы `NEXT_PUBLIC_GA4_ID` / `NEXT_PUBLIC_META_PIXEL_ID`. Админка не трекается.
- Purchase отправляется на `/thank-you` один раз на заказ (метка в localStorage): для наложенного платежа сразу, для карты только при статусе `PAID`.

### 5.6 Скорость на мобильном

- Сжатие фото в браузере при загрузке в админке (длинная сторона до 1600 px, WebP или JPEG). Бесплатно, не зависит от тарифа хостинга, и клиентке быстрее грузить фото с телефона.
- `next/image` для публичных картинок (карточка товара, галерея, баннер, плитки категорий) с правильными `sizes` и `priority` для первого экрана. Хост ограничен `*.supabase.co`, кэш оптимизированных картинок 31 день. Для картинок с других хостов предусмотрен откат на `unoptimized`.
- Кэширование публичных чтений (товар, главная, шапка) через уже используемый в проекте паттерн `unstable_cache` + теги со сбросом из админки. Это условная задача: делаем после замера на реальном деплое, если ответ сервера на странице товара медленный.
- Шрифты уже подключены через `next/font` (самохостинг, swap), менять не нужно.

### 5.7 Контент и юридические страницы

- Для Украины нужны: публичная оферта, политика конфиденциальности, условия доставки и оплаты, возврат и обмен (14 дней по закону о защите прав потребителей), контакты с реквизитами продавца (ФОП, РНОКПП, адрес, телефон). Это требования закона об электронной коммерции, эквайринга и рекламного кабинета Meta.
- Код готовит каркас: страницу `/oferta`, ссылки в футере, блок реквизитов из `site-config`, строку согласия на чекауте. Тексты остаются черновиками с плашкой `PlaceholderNotice`, пока клиентка (желательно с юристом) не даст финальные. Архитектор юридические тексты не утверждает.
- Отзывы: скриншоты кладутся файлами в `public/reviews/`, список в `src/content/reviews.ts`. Пока список пуст, блок на главной скрыт. Админку для отзывов не делаем (то же решение, что для обложек категорий).
- Обложки категорий и баннер: без изменений в коде. Баннер клиентка меняет сама в `/admin/homepage`, обложки разработчик подставляет вручную по прежней процедуре.

### 5.8 Тестовая стратегия (минимальная)

Владелец не тестировщик, поэтому проверяем то, где ошибка стоит денег, и только командой:

1. Юнит-тесты Vitest на чистые функции: расчет заказа, схема чекаута, переходы статуса оплаты, подписи LiqPay и Monobank (ключи генерируются в тесте, сеть подменяется), сборка событий аналитики, разбор UTM, формат сообщения Telegram, ограничитель запросов, расчет размеров при сжатии фото.
2. Тестов с реальной БД нет сознательно: связь с Supabase из окружения разработки нестабильна, а тест, пишущий в БД, это риск для данных. Логика вынесена из роутов в чистые функции именно ради этого.
3. Дымовой скрипт `npm run smoke` против запущенного сайта (локально или прод): ключевые страницы отвечают 200, админка закрыта, вебхук с плохой подписью отклоняется, невалидный заказ отклоняется. Ничего не пишет в БД.
4. CI в GitHub Actions: `typecheck`, `lint`, `test` на каждый push.
5. Ручная приемка полного пути покупки по чек-листу `docs/acceptance.md` на временном адресе Vercel с тестовым токеном Monobank.

Команды проверки для задач: `npm run typecheck`, `npm run lint`, `npm test`, для задач про маршруты и конфигурацию еще `npm run build`.

## 6. Правила работы с БД (обязательны для всех исполнителей)

- Запрещено без явного подтверждения владельца: `prisma migrate reset`, `prisma db push`, любые `deleteMany`/`DROP`/`TRUNCATE`, одноразовые скрипты, меняющие или удаляющие строки, запуск чего-либо против production-БД.
- `prisma/seed.ts` остается только добавляющим (upsert с `update: {}`), удалений в нем быть не должно.
- Миграции схемы только добавляющие (новая nullable-колонка, новая таблица). Если `prisma migrate dev` предлагает сброс базы или предупреждает о потере данных, исполнитель останавливается и сообщает оркестратору.
- Причина правила: 2026-11-07 пересев с `deleteMany` стер товары, внесенные вручную, восстановить их было нельзя.
